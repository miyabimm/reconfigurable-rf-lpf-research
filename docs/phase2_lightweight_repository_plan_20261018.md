## 0. 実態と問題設定

基準main `8e95acf9fa59cd3dc671f65b997698b3affbcf37`（PR #98統合後）を確認。

- **Git追跡ファイル：1,196件／合計およそ15.9 MB（各blobの非圧縮サイズの概数）**。Git履歴全体やGit packサイズではない。
- **workflow 48件**。歴史実験用28件（EXP-042/043/044系19件、旧LPF系9件）、運用基幹2件（`audit.yml`、`reserve_experiment_number.yml`）、その他の整理・監査・証拠検証系18件（PR #91のB/C統合監査を含む）。
- **`tests/` 97件、`scripts/` 74件**。この件数はファイル数であり、テストケース数・実行負荷を表す値ではない。
- **現行の`audit.yml`**はPR/pushごとに、全単体テスト、旧RF-F002 EXP-017の密な格子再計算、過去の証拠ZIP・candidate・Pareto・Git分岐・容量監査、実験メタデータ等をひとまとめに実行する。CIは研究工程の便利な道具だが、日常的な編集に対して過重。
- [PR #98](https://github.com/MasayaTakagi/reconfigurable-rf-lpf-research/pull/98)でPR #92の重複workflow1件は削除済み。main SHA上の[Phase 2回帰39117263327](https://github.com/MasayaTakagi/reconfigurable-rf-lpf-research/actions/runs/39117263327)はSUCCESS。これをさらに検証するための新たな常時監査は必要ない。
- 旧[47件分類](../data/repository_reviews/phase2_Bc_workflow_retention_proposals_20261018.csv)とW0～W5の記録は**作成時点の保全重視の歴史的基準**。今回の方針は以後の運用簡素化への**提案**であり、実行前にmainの採用判断を要する。

### オーバーエンジニアリングの原因

一時の出典確認を常設CI化→その移管のために別のCI→同一性の監査→別の出典台帳、という階層が増えた。研究成果の信頼性に寄与する重要な`物理モデル／条件／独立検証`と、古いGit blob・既存台帳の繰り返し照合を区別する。

**成功指標は「テスト合格数・監査台帳数」ではなく「最良結果を条件付きで読める・再実行できる・その限界が分かる」こと。**

## 1. 最終形（目標であり未実施）

### GitHub Actions：**48 → 2～3 workflow**を目指す

| 運用 | workflow | 新方針 |
|---|---|---|
| 常時の軽量チェック | `audit.yml`（名称は維持可能） | PRの**解析コード／制約／候補データ**変更時のみ、軽量・短時間のスモークチェック。docsだけの変更時には原則走らせない |
| EXP番号の重複防止 | `reserve_experiment_number.yml` | main事前予約ルールが現行運用なので保持。将来簡素化する場合も番号衝突対策を維持 |
| 大規模探索 | **共通の手動実行workflow 0～1件** | GitHub Actionsを使う探索が必要な場合のみ新設。対象runner/EXP ID/制約IDを許可リストで選び、任意シェル実行を許さない。既存28個の実験固有workflowを恒常維持しない |

**日常CIの検査**は、(1)現行RF制約・周波数帯・固定S2Pの整合、(2)候補/manifestの重要フィールドと完全ベクトル、(3)現行回路解析・負荷計算の代表的なスモークテストを基本とする。**一度に10～20の代表的なテストケース**を暫定の規模目標にするが、数字より壊れやすい数値機能の保護を優先する。

以下は**常時CIから外し、必要な時に既存コマンドを手動実行**：
- 旧RF-F002の28区間×7,001点検証、EXP-042元ZIP/19member・EXP-046/047 131原本の出典監査、W0～W5の整理監査。
- 97個のテストファイル全件の反復実行、過去のGitブランチ/サイズ/リンクの全量棚卸し、候補/パレート/ZIPレポートのPRごとの再生成。
- 変化のない原本を何度もハッシュ照合して、退役済みworkflow同等性を検証する仕組み。

RF数値モデルの実質変更時、重要候補の昇格時、新しい成果の公開前には、**関連する数値テストと独立MNA／共通格子照合を都度実行**する。未実行は未実行と明記し、旧CIのPASSを新設計性能に流用しない。

### 原則として保持する研究成果

- 現行`data/constraints/registry.json`、正式`RF-F003.json`、試験`RF-T005.json`、`bands.csv`、2つの固定S2PとSHA、共通解析実装、依存環境固定`uv.lock`。
- 実験番号台帳、**制約IDごとに分離された候補の完全回路ベクトル**（L/C/結合係数と全6設定の可変C）、代表的なパレート点（RF-T005の保存済み6点／RF-F003の保存済み4点、および再検証・反例に必要な他の点）。
- 最終結果のIL/H2/H3、チップ面積、評価帯域・格子、収束/中断/未検証状態、重要な失敗と負例、独立数値検証の結果と元データの訂正根拠。
- **実行を復元する条件**：EXP ID、目的、コードGit commit（dirty作業ツリーならソースの保管先）、実行コマンドと引数、入力SHA、制約/S2P SHA、seed（不明なら不明）、Python/依存バージョン、必要な代表ログ・終了状態・再開checkpoint。
- 旧EXP-047の元manifestや訂正前・訂正後の記録、EXP-042の元ZIPなど、**ほかに保存されていない情報を含む一次証拠**。

### 新規実験の推奨最小構成

```text
experiments/.../EXP-NNN/
  README.md           # 目的／回路・探索方法／最終結果／考察／未達／再現方法
  manifest.json       # 制約ID・SHA／コードcommit／環境／コマンド／seed／終了状態
  results.json        # 有望・パレート・反例の完全ベクトルと数値結果
  validation.json     # 検証器・評価帯域・実行有無・数値・未検証項目
  repro.log           # 必要最小の代表ログ、エラー／再開情報（あれば）
```

既に別の場所に同じ役割の原本があるなら**同名ファイルを増やさず、READMEからリンク**する。各実験のREADMEは、最良値だけでなく、何が効いたか、何が失敗したか、次に何を試すかを短く記述する。生の全worker出力、逐次iteration dump、cache、冗長なJSONコピー、成功しただけの長大なstdoutは基本的に残さない。

**再現の意味を3段階に分ける**：（A）最終候補を同じ条件で再評価可能、（B）元の探索手順を再実行可能、（C）元の探索の全ステップを同一結果で再現可能。通常は**Aを必須**、重要成果や将来の新規runでは**Bを目標**。seed/環境欠損がある旧runのCを偽って主張しない。

## 2. 削減対象と単純な判断規則

| 対象 | 新しい標準判断 | 削除前に最低限確認すること |
|---|---|---|
| **28個のEXP/旧LPF専用workflow** | 原則終了・退役候補 | 原Git SHAと固有の実行コマンド/引数・使用コードが確認でき、重要成果の再現経路が残る |
| **18個の整理・証拠監査workflow** | 原則退役候補（PR #91正本監査も常設不要なら退役） | 一次証拠と必要な手動検査スクリプトを残す。過去runの固定結果は変更しない |
| **97個のテストファイル** | 日常CIでの全量実行を廃止。歴史仕様だけを検証するテストは整理 | 現行RF回路の解析、RF-F003/T005区分、候補ベクトル・独立検証の数値保護を損なわない |
| **74個のscripts** | 現行runner・再現・数値検証に使うものを入口へ。過去の一度限りの監査スクリプトは整理 | 元の実行コマンドを保存し、必要時に固定Git commitから取り出せる |
| **88個のdocs/** | 入口を現行結果・未解決課題・再現手順に集約 | 歴史的な考察・訂正事実が現行から消える場合は履歴リンクを残す |
| **古い中間JSON・trace** | 一次証拠・代表反例以外は小さい結果に集約可能 | 固有ベクトル・失敗理由・再開点・出典/検証条件を損なわないことを個別に判定 |

`tests/`と`scripts/`の**削除件数の目標は事前固定しない**。残すべき機能が多ければ残す。主要な最終目標は**workflowを2～3に収束し、普段の変更から重い回帰処理を外すこと**。

以前の保存方針で棚卸した元225件には、**128件の必須一次証拠、81件の同等性未確認資料、16件の集約検討資料**が含まれる。旧225件の分類を根拠に自動削除しない。重要な元実験・訂正根拠・最終候補・独立検証を保持したうえで、必要が薄い中間ファイルを実データベースで判断する。

**Git履歴の注意**：Git追跡treeから削除しても、過去のGit blobやcommitは通常Git履歴に残る。新しいcheckoutの理解容易性は上がるが、Git packディスク量がその分だけ減るとは限らない。履歴rewrite/force pushによる実容量圧縮は**本計画の対象外**。

## 3. 実施順序（研究の「Phase 3」と混同しない整理工程）

**Step A：まず日常CIを縮小**（最優先）
- `audit.yml`を最小の軽量テストへ分割・短縮する。docs変更だけで全数値再計算しない。
- 現行仕様の重要な回路モデル検査は残し、full regression、歴史的出典監査、独立MNA、大規模計算は`uv run ...`による**手動の再現手順**としてREADMEに固定。
- 目標：日常CI**数分以内**。実測値を導入後に記録し、遅い場合は本質的なテストが失われない範囲でさらに減らす。

**Step B：workflowをまとめて整理**
- 対象48件を「常時必要／共通手動runnerに移管／Git履歴から復元可能な終了済み」の3区分に短く分類する。詳細な新しい監査体系は作らない。
- 研究用28件、整理監査18件を数回の**対象パスを列挙したバッチPR**で退役する。1件ごとに独立したCI・巨大なSHA台帳・専用監査workflowは作らない。
- 各バッチで残す記録は**対象ファイル一覧、元main SHA、実行・復元コマンド、例外、PR URL**だけにする。外部システムが無い前提なので外部チェック利用者の有無を追わない。削除後、重要な再現例を1系統だけスモーク確認する。
- 既存のworkflowにしかない探索用パラメータやコード断片がある場合、Gitの固定commit/元pathを再現手順に記し、**必要なものだけ**小さな共通runnerへ移管してから削除。すべてを実行し直してからでないと退役できない、という一律ゲートは設けない。

**Step C：テスト／スクリプトの整理**
- `tests/`は「現行モデルの重要テスト」「変更時に使う重い数値試験」「旧仕様専用」に分類し、日常CIには最初だけを残す。後者はコマンド案内だけ残して削除／歴史から復元を段階判断。
- `scripts/`のうち、探索・再評価・独立検証・候補集約に使うスクリプトをREADMEから明示。W0～W5のような一時監査スクリプトや中間台帳生成専用スクリプトは、固定Git commitと重要な結果を保存してから段階退役する。
- 旧仕様テストと旧探索コードを**重要な再現性があるのに一律削除しない**。数値演算器そのものは手動でもテスト可能な状態を維持する。

**Step D：成果と文書を整理**
- 最も見る場所を`README.md`、`docs/current/phase2_status.md`、`docs/results/README.md`、各`EXP-NNN/README.md`、最小の`REPRODUCE.md`に限定する。長い歴史説明は固定Git commit参照へ。
- 元225件のうち中間JSON・traceから**最終数値、完全ベクトル、選別理由、代表ログ、再現メタデータ**だけを抽出したものを作成。ただし、独立した固有実験証拠は残す。最初は16件の集約候補に限定して実例を確認。
- 削減結果を「workflow数／通常のCI時間／現行READMEの導線／新規実験1件の再評価可能性」で評価し、台帳の数は成功指標にしない。

## 4. 最小限の承認・品質基準

- **この計画の作成＝全48 workflowや元225原本の削除承認ではない。** 実削除する段階で、ユーザーが明示承認した**対象パス一覧を含むバッチ**ごとにPRを作る（1件ずつのPRは不要）。合意済みの最新方針は以後の提案に優先して用いる。
- 無関係な監査のCIがPASSすることを目的化しない。**削除対象に実体のある再現コード・入力・重要ログが含まれないこと**、最小CIが通ること、リンクが壊れないことを実務上の受入条件にする。
- formal `RF-F003`、trial `RF-T005`、28周波数区間／6設定の区分、IL/H2/H3ゲート、固定S2P、重要な訂正根拠、独立解析の成否は削減対象外。
- 実行済み・未実行・未収束・旧条件を引き続き明示する。新たなRF数値探索・Phase 3移行は本整理作業に含まれない。

## 5. 優先度と成功判定

1. **最優先：Step A** — 現行`audit.yml`の全量常時回帰を軽くする。使わない機能の同等性を永久にチェックしない。
2. **次：Step B** — 48 workflowを**最終的に2～3**へ集約することを目指し、削除パスをまとめた実施PRを提案。
3. **次：Step C/D** — 97テストファイルと74スクリプト、長い文書・中間結果を用途別に短くする。再現可能性を失わない範囲で削減。

**現時点の区分**：提案文書作成のみ。新CI実装、workflow一括退役、元研究結果集約、個別ファイル削除、数値追試は**未実施**。mainへの反映はPRで別途確認する。
