## 3. 二方式による回路トポロジー探索

### A. ChatGPT主導の理論探索

磁気結合による実効Q向上、低Q素子電流の削減、反射損失低減、共振・反共振・伝送零点、マルチモード結合、入力出力整合と阻止機能の統合を用いて新回路を考案する。

- 有望な構成ごとに高速な専用解析・最適化器を作る。
- 固定L/C、結合係数、各設定の可変Cを適切な制約下で同時最適化する。
- 2つの対GND可変Cから複数の伝送零点に作用できる構造、固定GJM01/PCBパターンCの再配置、小さいL値への再合成を重視する。
- 回路構造に対して厳密に成立する場合に限り、解析高速化のための等価回路縮約を用いる。

### B. スクリプト主導の体系的探索

回路グラフを生成し、汎用MNAと数値最適化で有限のトポロジー集合を体系的に評価する。

- 探索対象の有限範囲、枝種別、結合配置、サンプル数を明記し、実験の計算上限を正式RF制約と混同しない。
- グラフ生成・重複排除・初期値継承など、再利用可能な解析・探索部品は共通コードとして扱う。新しいPi探索方式の実装・実測は別途確認する。

### C. 相互補完

AI考案回路をグラフ探索のシードにし、グラフ探索の良好解には専用高速最適化器を用いる。既存の検証済みL/C値を初期値に再利用する。**最終確認は独立した汎用MNA解析**で行う。両方式の探索済み領域と未探索領域を明確にする。

## 4. 最適化と計算インフラ

最適化器は、一律の処理を機械的に適用せず、構造に応じた効率と解の品質を重視する。

- SLSQP等の制約付き最適化、epigraph minimax、多初期値、継続法、適応的最悪周波数グリッドを定量比較する。

### 7.1 開発・レビューの標準フロー

- **ユーザー（プロジェクトオーナー）：** 研究方針、優先順位、重要な科学的仕様変更、未承認の新規EXP・本番計算の実施、重要データの変更、研究段階の移行を最終承認する。
- **ChatGPT（研究PM兼独立テクニカルレビュー）：** ロードマップとIssueを整理し、回路考案・解析方針を主導する。実際のGitHub差分・テスト・実験証拠を独立にレビューし、修正指示と次工程を管理する。実装担当の自己申告だけで合格としない。
- **実装担当：** 現時点ではCodex等の利用可能な手段を活用する。Pi Codeは導入後、Issue・PRコメントに従って実装、検証、push、Draft PR作成を担当する。**Pi Codeのローカル探索実行器が実装済みとはみなさない**。
- 重要な作業は**既存資料の確認 → 目的・スコープ・RF制約ID・完了条件（DoD）を明記したIssue → 最小限の実装・検証 → Draft PR → ChatGPTの独立レビュー → 必要な修正・再レビュー → 委任範囲内でのマージ → main反映確認と次工程**で管理する。軽微な修正は過剰なIssue分割を避ける。
- PRには変更内容、検証した条件、実際に実行したチェックと結果、未解決事項、HEAD SHA、PR URLを残す。**Issue作成やPR作成は、実験実施・科学的達成・次フェーズ移行の承認を意味しない**。

### 7.2 KISS・YAGNIと必要十分な検証

- **正確性を維持するために必要な最も単純な実装**を選び、将来の可能性だけの抽象化、仮想的な異常への重複防御、無関係なリファクタリングを避ける。既存の解析器・共通コード・テスト機構を優先して再利用する。
- テストは主要動作、RF/数値上の不変条件、現実的な境界、確認済み不具合の再発防止に集中する。追加テストの目的を明確にし、既存テストで十分なら増やさない。**テスト数・網羅率の最大化を目的としない**。
- レビューでは仕様適合性、物理・数値計算の正しさ、再現性、実測・実行証拠、回帰リスクとDoDを優先する。問題の重大度・発生可能性・修正コストに応じて対応し、軽微な仮説だけでスコープを拡大しない。不要な複雑さの削減もレビュー対象とする。
- **科学的に不可欠な検証は簡素化の対象外**とする。適用条件に応じて全6設定・不連続帯域・H2/H3、結合行列SPD、受動性・電力保存、固定S2P、独立MNA、制約ID・ソース指紋と結果の追跡可能性を確認する。コード上のテストPASSとRF適合・実験承認・物理実装可能性・科学的結論を区別する。

### 7.3 承認境界と研究の自律性

- **承認済みのPhase 2条件と作業範囲内**では、回路仮説の考案、理論計算、小規模な検証、通常の実装・レビュー・進捗管理を自律的に進める。
- RF正式/試験条件や物理モデルの科学的意味、探索評価条件・予算の重要な変更、新規EXPや大規模本番計算の実施、重要な保存結果・チェックポイントへの変更は、**既に明示承認・委任された範囲を除き**事前にユーザー承認を得る。承認事項はIssueや記録で範囲を明確化する。
- **設計案の承認、ソフトウェア検証の合格、数値実験実施の承認、有限探索による観測結果、科学的結論は相互に別**である。CI成功やPRマージだけで探索完了・性能改善を主張しない。
- 数値探索を不必要に官僚化せず、既存の独立検証・main事前EXP番号予約・重要証拠保全を遵守する。研究はPhase 2を維持し、**Phase 3へはユーザーの別途明示承認なく進まない**。
